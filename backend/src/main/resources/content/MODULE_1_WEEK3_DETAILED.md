### LESSON 15.1: Understanding Daily Standup Purpose (20 хвилин)

#### What is Daily Standup?

**Definition:**
A short daily meeting (5-15 minutes) where team members share:
1. What they did yesterday
2. What they're doing today
3. Any blockers/impediments

**Origins:** Agile/Scrum methodology

**Why "standup"?**
- Originally done standing to keep it short
- Now often done remotely (still called standup)

---

#### The Purpose - Why It Matters:

**For the Team:**
- ✅ Synchronization - everyone knows what's happening
- ✅ Early problem detection - blockers identified quickly
- ✅ Coordination - avoid duplicate work
- ✅ Accountability - public commitment to tasks

**For You:**
- ✅ Practice concise communication
- ✅ Visibility - people know what you're working on
- ✅ Get help - surface blockers early
- ✅ Build credibility - consistent delivery

**For Management:**
- ✅ Project status overview
- ✅ Resource allocation
- ✅ Risk identification
- ✅ Team health check

---

#### Common Standup Formats:

**Format 1: Classic Three Questions**
```
1. What did I do yesterday?
2. What will I do today?
3. Are there any blockers?
```

**Format 2: Task-Based**
```
"I'm working on [ticket/task]. Yesterday I [progress]. 
Today I'll [plan]. [Blocker if any]."
```

**Format 3: Goal-Oriented**
```
"My goal is [outcome]. I've completed [steps]. 
Next I'm [action]. [Status: on track / blocked]."
```

---

#### Standup Anti-Patterns (What NOT to Do):

❌ **Too Long** (over 2 minutes)
```
"So yesterday I started by checking my emails, then I had a coffee, 
then I opened the ticket, then I read the requirements, then I had lunch, 
then I started coding, but first I had to set up my environment..."
[This is a story, not an update]
```

✅ **Concise** (60-90 seconds)
```
"Yesterday I implemented the user authentication API endpoint. 
Today I'm adding tests and documentation. No blockers."
[Clear, specific, brief]
```

---

❌ **Too Vague**
```
"Yesterday I worked on stuff. Today I'll work on more stuff. No blockers."
[Provides no useful information]
```

✅ **Specific**
```
"Yesterday I fixed the login bug in ticket #234. Today I'm refactoring 
the authentication service. No blockers."
[Team understands exactly what's happening]
```

---

❌ **Problem Solving** (using standup to solve issues)
```
"I'm blocked because the API isn't working. So we need to discuss 
whether we should refactor the whole authentication system, and maybe 
we should consider OAuth, or perhaps JWT tokens..."
[Takes too long, involves only some people]
```

✅ **Flag and Defer** (identify problem, solve later)
```
"I'm blocked on the API authentication issue. Can someone help me 
with this after standup?"
[Quick flag, detailed discussion happens separately]
```

---

❌ **Status Report to Manager** (treating it like reporting up)
```
"I completed task A, B, and C as assigned. I will now proceed 
with tasks D and E per the project plan..."
[Sounds like a report, not a team sync]
```

✅ **Peer Update** (talking to your team)
```
"I finished the payment integration. Moving to the order processing 
next. Let me know if anyone needs that API - it's ready."
[Collaborative tone, offering to help]
```

### LESSON 15.2: Structuring Your Standup Update (25 хвилин)

#### The Perfect Standup Formula:

```
[YESTERDAY: Past Simple] + [TODAY: Future/Present Continuous] + [BLOCKERS: if any]
```

**Time:** 60-90 seconds maximum

---

#### Part 1: YESTERDAY (20-30 seconds)

**Grammar Focus: Past Simple**

**Template:**
```
"Yesterday I [completed action] + [specific result/output]"
```

**Good Examples:**

```
Example 1 - Feature Complete:
"Yesterday I finished implementing the user profile page. 
It's now ready for review."

Example 2 - Progress Made:
"Yesterday I worked on the authentication service. 
I completed the login endpoint and started on logout."

Example 3 - Bug Fixed:
"Yesterday I fixed the critical bug in the payment flow. 
Tested it and deployed to staging."

Example 4 - Research/Investigation:
"Yesterday I investigated the performance issue. 
Found the bottleneck in the database queries."

Example 5 - Meeting/Coordination:
"Yesterday I met with the design team to clarify the new UI requirements."
```

**Structure Variations:**

**Achievement-focused:**
```
"I completed [task]. This means [impact/next step enabled]."

Example:
"I completed the API documentation. This means the frontend team 
can start integration."
```

**Progress-focused:**
```
"I made progress on [task]. [What's done], [what remains]."

Example:
"I made progress on the search feature. Backend is done, 
working on frontend now."
```

**Multiple Tasks:**
```
"I worked on two things: [task 1] and [task 2]."

Example:
"I worked on two things: finished the user endpoint and 
reviewed three PRs from the team."
```

---

#### Part 2: TODAY (20-30 seconds)

**Grammar Focus: Future forms (will / going to) or Present Continuous**

**Template:**
```
"Today I'm [doing action] / I'll [do action] / I'm planning to [do action]"
```

**Good Examples:**

```
Example 1 - Clear Plan:
"Today I'm implementing the logout functionality and adding unit tests."

Example 2 - Multiple Tasks:
"Today I'll finish the authentication service and start on password reset."

Example 3 - Review/Collaboration:
"Today I'm reviewing the PRs from yesterday and helping with the deployment."

Example 4 - Continuation:
"Today I'm continuing work on the payment integration. 
Aiming to have it ready for testing by end of day."

Example 5 - Specific Goal:
"Today my goal is to get the user dashboard feature to code complete."
```

**Time Indicators (helpful for clarity):**

```
"This morning I'll [task 1]. This afternoon [task 2]."

"I'm starting with [task], then moving to [task]."

"First priority is [task], then if time allows, [task]."
```

---

#### Part 3: BLOCKERS (10-30 seconds, only if present)

**Template:**
```
"I'm blocked on [specific issue]. [What you need] / [Who can help]."
```

**Types of Blockers:**

**1. Waiting on Others:**
```
"I'm blocked waiting for the API spec from the backend team."
"I'm blocked waiting for design approval on the mockups."
"I need the staging environment to be fixed before I can test."
```

**2. Technical Issues:**
```
"I'm stuck on a TypeScript compilation error. Could use another pair of eyes."
"I'm blocked on this authentication issue. Need help figuring it out."
"The CI/CD pipeline is failing. Not sure why yet."
```

**3. Missing Information:**
```
"I need clarification on the requirements for the user flow."
"I'm blocked waiting for the client to provide the integration credentials."
"Not sure which approach to take here - need a technical discussion."
```

**4. Resource/Access Issues:**
```
"I don't have access to the production database yet."
"I need the license key for [tool] to continue."
"The dev environment is down - can't test my changes."
```

**How to Present Blockers:**

✅ **Good - Clear and Action-oriented:**
```
"I'm blocked on X. [Name], can you help me with this after standup?"
[Specific person, clear ask, time-bound]

"I'm blocked waiting for Y. When can we expect that to be ready?"
[Clear question, looking for timeline]

"I'm stuck on Z. I'll post details in Slack - anyone who's dealt 
with this before, please chime in."
[Clear plan to get unblocked]
```

❌ **Bad - Vague or Complaining:**
```
"I'm blocked on everything."
[Not specific, not helpful]

"The backend team is slowing me down."
[Blaming, not collaborative]

"I don't know what to do."
[Not actionable, need to be more specific]
```

---

#### Complete Standup Examples:

**Example 1 - Smooth Progress:**
```
"Yesterday I completed the user registration API endpoint. 
It's merged and deployed to staging. Today I'm moving on to 
the login endpoint. Should have that done by end of day. 
No blockers."

[Time: ~20 seconds]
```

---

**Example 2 - With Blocker:**
```
"Yesterday I worked on the payment integration and got about 
70% through it. Today I'm finishing up the integration and 
adding error handling. I'm blocked on one thing - I need the 
test API credentials from the payment provider. [Manager], 
can you help me get those?"

[Time: ~30 seconds]
```

---

**Example 3 - Multiple Tasks:**
```
"Yesterday I did two things: finished the database migration 
script and reviewed three PRs. Today I'm deploying the migration 
to staging and starting on the caching layer implementation. 
No blockers."

[Time: ~25 seconds]
```

---

**Example 4 - Investigation/Research:**
```
"Yesterday I investigated the performance issue in the API. 
Turns out it's a database indexing problem. Today I'm implementing 
the fix and running performance tests to validate it. No blockers."

[Time: ~25 seconds]
```

---

**Example 5 - Collaboration Heavy:**
```
"Yesterday I paired with [name] on the frontend integration. 
We got the authentication flow working. Today I'm solo again - 
adding the refresh token logic and documenting the API. 
No blockers."

[Time: ~25 seconds]
```

### LESSON 16.1: The Psychology of Asking for Help (20 хвилин)

#### Why Developers Struggle to Ask for Help:

**Common Mental Blocks:**

1. **"I should know this"**
   - Imposter syndrome
   - Fear of looking incompetent
   - Perfectionism

2. **"I'm bothering them"**
   - Don't want to interrupt
   - Feel guilty taking their time
   - Worried about being annoying

3. **"I should figure it out myself"**
   - Independence valued in tech
   - Pride in problem-solving
   - Previous culture (school, bootcamp)

4. **"They'll think I'm stupid"**
   - Fear of judgment
   - Comparing to others
   - Lack of confidence

---

#### Reality Check - Why Asking IS Professional:

**Truth 1: Everyone Needs Help**
```
Junior dev: "I need help with React hooks"
Senior dev: "I need help with this system design decision"
Tech Lead: "I need help prioritizing these features"
```
→ Needing help is normal at ALL levels

**Truth 2: Asking Saves Time**
```
Scenario A: Struggle alone for 4 hours, maybe solve it
Scenario B: Ask after 30 min, get answer in 5 min, move forward
```
→ Asking is efficient, not lazy

**Truth 3: People WANT to Help**
```
Most developers:
✅ Enjoy helping others learn
✅ Feel valued when asked
✅ Remember when they needed help
✅ See it as team building
```
→ You're not bothering them

**Truth 4: Asking Shows Maturity**
```
Junior behavior: Pretend to know, produce bad work
Senior behavior: "I need help with X because Y"
```
→ Asking is a sign of professionalism

---

#### When to Ask for Help:

**The 30-Minute Rule:**
```
If you're stuck for 30+ minutes with no progress:
→ Time to ask for help

Exception: If it's blocking others
→ Ask sooner (after 10-15 min)
```

**Signs You Should Ask:**
- ✅ You've googled extensively, no luck
- ✅ You're going in circles
- ✅ You don't understand the problem itself
- ✅ You're blocked and can't proceed
- ✅ You've tried 3+ different approaches

**Before Asking, Do:**
1. Try to solve it yourself (20-30 min)
2. Google the error / issue
3. Check documentation
4. Understand what you DON'T understand
5. Prepare your question

---

### LESSON 16.2: How to Ask for Help - The Framework (25 хвилин)

#### The Perfect Help Request Formula:

```
[CONTEXT] + [WHAT YOU TRIED] + [SPECIFIC QUESTION] + [URGENCY]
```

---

#### Component 1: CONTEXT (What you're working on)

**Template:**
```
"I'm working on [task/feature]. I'm trying to [goal]..."
```

**Examples:**
```
"I'm working on the user authentication API. I'm trying to 
implement JWT token validation..."

"I'm working on ticket #234, the profile page. I'm trying to 
connect it to the backend API..."

"I'm implementing the payment integration. I'm trying to set up 
the webhook handler..."
```

**Why This Matters:**
- Helps them understand the bigger picture
- They can suggest alternative approaches
- Shows you understand your task

---

#### Component 2: WHAT YOU TRIED (Shows you made an effort)

**Template:**
```
"I tried [approach 1], [approach 2], but [result]..."
```

**Examples:**
```
"I tried using the standard JWT library, and also tried implementing 
it manually, but I'm getting validation errors..."

"I tried following the API documentation, and also looked at the 
example code, but I'm still getting a 401 error..."

"I tried debugging with console logs and using the debugger, 
but I can't figure out where the data is getting lost..."
```

**Why This Matters:**
- Shows you're not lazy
- Prevents them suggesting what you already tried
- Helps them narrow down the issue
- Demonstrates problem-solving skills

---

#### Component 3: SPECIFIC QUESTION (What you need)

**Template:**
```
"[Specific question]? / Can you help me [specific thing]?"
```

❌ **Bad (Too Vague):**
```
"Can you help me with this?"
"I don't understand this."
"This isn't working."
```

✅ **Good (Specific):**
```
"Can you help me understand how the token validation works?"
"Do you know why I'm getting this specific error message?"
"Can you show me an example of how this API should be called?"
```

**Types of Specific Questions:**

**Type 1: Understanding Concept**
```
"Can you explain how [concept] works?"
"I don't understand [specific part]. Can you clarify?"
"What's the difference between [X] and [Y]?"
```

**Type 2: Solving Technical Problem**
```
"Why am I getting [specific error]?"
"How do I [specific technical task]?"
"What's the correct way to [do X]?"
```

**Type 3: Code Review/Feedback**
```
"Can you review my approach to [task]?"
"Is this the right way to implement [feature]?"
"Can you spot what I'm doing wrong here?"
```

**Type 4: Direction/Clarification**
```
"Should I implement this using [approach A] or [approach B]?"
"What's the priority here?"
"Am I on the right track with this?"
```

---

#### Component 4: URGENCY (When you need it)

**Template:**
```
"[Urgency level]. [When you need it by]."
```

**Examples:**

**High Urgency:**
```
"This is blocking me. Can you help me now or point me to someone who can?"
"I need to deploy this today. Can you help me soon?"
```

**Medium Urgency:**
```
"Not super urgent, but I'd appreciate help when you have time today."
"Can we discuss this sometime today?"
```

**Low Urgency:**
```
"No rush - when you have time this week."
"I'll keep trying, but if you have insights, I'd appreciate them."
```

**Why This Matters:**
- Respects their time
- Helps them prioritize
- Sets expectations

---

#### Complete Help Request Examples:

**Example 1: Slack Message (Async)**

```
Hey [Name], quick question about the authentication system.

[CONTEXT]
I'm working on implementing the password reset feature (ticket #456). 
I'm trying to generate and validate the reset tokens.

[WHAT YOU TRIED]
I tried using the same JWT approach as login, and also looked at 
the forgot-password-service in the auth module, but I'm not sure 
how to set the expiration time correctly for reset tokens.

[SPECIFIC QUESTION]
Can you point me to an example of how we handle time-limited tokens? 
Or explain the approach we should use?

[URGENCY]
Not blocking me yet - I have other tasks. But would be helpful to 
know by end of day.

Thanks!
```

**What Makes This Good:**
- ✅ Context provided
- ✅ Shows effort (tried two approaches)
- ✅ Specific question
- ✅ Clear urgency level
- ✅ Polite and professional

---

**Example 2: In-Person/Video Call Ask**

```
"Hey [Name], do you have 5 minutes? I'm stuck on something.

[CONTEXT]
I'm working on the user profile API endpoint.

[WHAT YOU TRIED]
I followed the pattern from the other endpoints, but I'm getting 
a 500 error when I try to update the profile. I've checked the 
request payload and it looks correct.

[SPECIFIC QUESTION]
Can you help me debug this? I'm not sure where to look next.

[URGENCY]

```

---

**Example 3: During Standup**

```
"[After your update] One more thing - 

[CONTEXT]

[WHAT YOU TRIED]

[URGENCY]

```

### LESSON 16.3: Different Asking Scenarios (15 хвилин)

#### Scenario 1: Asking Your Manager

**Tone:** Professional, structured
**Channel:** Slack DM, 1-on-1, email

```
"Hi [Manager],

I wanted to ask for your input on [topic].

[Context + What you tried + Question + Urgency]

Let me know when would be a good time to discuss.

Thanks!"
```

**Example:**
```
"Hi Sarah,

I wanted to ask for your input on the architecture approach 
for the new reporting feature.

I've researched two approaches: building it as a microservice 
vs extending the existing monolith. Each has tradeoffs around 
development time vs future scalability.

What's your recommendation given our current priorities?

Not urgent - would be good to align on this before I start 
coding next week.

Thanks!"
```

---

#### Scenario 2: Asking a Senior Dev/Tech Lead

**Tone:** Respectful, show you've done homework
**Channel:** Slack DM, in-person

```
"Hey [Name], I could use your expertise on something.

[Context + What you tried + Specific question]

Do you have time to chat about this? Or should I write it 
up in more detail?"
```

**Example:**
```
"Hey Alex, I could use your expertise on the caching strategy.

I'm implementing the product catalog API and trying to figure out 
the right caching approach. I've read about Redis patterns and 
looked at how we cache user data, but product data seems different 
since it updates frequently.

Should we cache aggressively and invalidate often, or cache less 
and accept more DB hits?

Do you have 10 minutes to chat about this?"
```

---

#### Scenario 3: Asking a Peer

**Tone:** Casual but clear
**Channel:** Slack, in-person

```
"Hey! Quick question - [question]?"

Or for longer:

"Hey, got a sec? I'm stuck on [thing]. 
[What you tried]. Any ideas?"
```

**Example:**
```
"Hey Maria! Quick question - have you worked with the email 
service before? I'm getting weird timeout errors and not sure 
why.

I checked the logs and the config looks right. Any ideas what 
might cause this?

Thanks!"
```

---

#### Scenario 4: Asking in Public Channel (Team Chat)

**When:** Non-urgent, might benefit others, general question

```
"Hey team, question about [topic]:

[Context + Specific question]

Anyone have experience with this?"
```

**Example:**
```
"Hey team, question about deployment process:

I'm deploying the new API changes to staging. Should I restart 
the services manually or does the CI/CD handle that automatically?

Anyone know the current process?"
```

### LESSON 17.1: The Art of Offering Help (25 хвилин)

#### Why Offering Help Matters:

**Benefits:**
- ✅ Builds team culture
- ✅ Establishes you as collaborative
- ✅ You learn while helping
- ✅ Creates reciprocity (they'll help you later)
- ✅ Increases your visibility
- ✅ Develops mentorship skills

---

#### When to Offer Help:

**✅ DO Offer When:**

1. **You have relevant expertise**
```
Them: "I'm struggling with Docker configuration"
You (if you know Docker): "I've worked with Docker a lot. 
Want me to take a look?"
```

2. **You notice they're stuck**
```
[In standup]
Them: "Still blocked on the database migration issue"
You: "I dealt with something similar last month. 
Happy to share what worked for me."
```

3. **You have spare capacity**
```
Them: "This is taking longer than expected"
You: "I finished my tasks early. Want me to pair with you on this?"
```

4. **It's your responsibility area**
```
Them: "Not sure how to use the authentication service"
You (if you built it): "That's my area. Let me show you how it works."
```

5. **They explicitly asked**
```
Them (in channel): "Anyone familiar with GraphQL?"
You: "I've used it in several projects. What's your question?"
```

---

**❌ DON'T Offer When:**

1. **You don't actually have time**
```
❌ "Sure, I can help!" 
[Then ghost them because you're swamped]

✅ "I'm swamped today, but I can help tomorrow if that works?"
```

2. **You don't know the answer**
```
❌ Offering help, then wasting their time while you figure it out

✅ "I'm not sure about that, but [Person] might know. Want me to connect you?"
```

3. **They didn't ask (and seem fine)**
```
❌ Unsolicited "let me show you a better way"
[Can come across as condescending]

✅ Wait for them to ask, or ask "Would feedback be helpful?"
```

4. **It would derail your priority work**
```
❌ Helping with low-priority task while your deadline approaches

✅ "I'd love to help but I'm on a deadline. Can we connect [later time]?"
```

---

#### How to Offer Help - The Framework:

**Formula:**
```
[ACKNOWLEDGE] + [OFFER SPECIFIC HELP] + [TIME/AVAILABILITY]
```

---

**Component 1: ACKNOWLEDGE**

Show you heard and understand:

```
"I heard you mention [problem]..."
"I noticed you're working on [challenge]..."
"Sounds like you're stuck on [issue]..."
```

---

**Component 2: OFFER SPECIFIC HELP**

Be clear about what you can offer:

❌ **Vague:**
```
"Let me know if you need help"
[Too generic, they might not follow up]
```

✅ **Specific:**
```
"I can show you how I solved this before"
"I can review your code if that would help"
"I can pair with you on this for an hour"
"I can point you to some good documentation"
```

**Types of Help You Can Offer:**

**Type 1: Knowledge Sharing**
```
"I can explain how [system] works"
"I can share the approach I used"
"I know a good resource for this"
```

**Type 2: Hands-on Help**
```
"I can pair with you on this"
"I can take a look at your code"
"I can help you debug this"
```

**Type 3: Connecting to Resources**
```
"I can introduce you to [person] who knows this well"
"I can share the documentation I used"
"I can point you to similar code in our repo"
```

**Type 4: Review/Feedback**
```
"I can review your approach"
"I can look at your PR"
"I can give feedback on your design"
```

---

**Component 3: TIME/AVAILABILITY**

Set clear expectations:

```
"I have 30 minutes now if you want to chat"
"I'm free after 3pm today"
"I can help tomorrow morning"
"I can take a quick look now, or we can schedule something longer"
```

---

#### Complete Offer Examples:

**Example 1: In Standup**

```
Them: "I'm blocked on the Redis caching implementation. 
Not sure about the best pattern to use."

You: "[ACKNOWLEDGE] I heard you're stuck on Redis caching. 
[OFFER] I've implemented caching in a few services before. 
I can share the patterns I used and maybe review your approach. 
[TIME] I'm free right after this standup if you want to chat."
```

---

**Example 2: Slack Response**

```
Them (in channel): "Anyone familiar with the deployment pipeline? 
Getting some weird errors."

You: "[ACKNOWLEDGE] I see you're having deployment issues. 
[OFFER] I've dealt with the pipeline a lot. 
Can you share the error message? I can probably point you in the right direction. 
[TIME] Available now for next hour."
```

---

**Example 3: Peer Check-in**

```
You: "[ACKNOWLEDGE] Hey, I noticed you've been working on the payment 
integration for a while. How's it going? 
[OFFER] I did the initial version of that - happy to answer questions 
if you have any. 
[TIME] No pressure, but I'm around if helpful."
```

---

**Example 4: Code Review Offer**

```
Them: "Finally got this feature done. Took forever!"

You: "[ACKNOWLEDGE] Nice work getting it done! 
[OFFER] Want me to do a quick review before you submit the PR? 
Always helpful to get fresh eyes. 
[TIME] I can look at it this afternoon."
```

### LESSON 17.2: Collaborative Communication (20 хвилин)

#### Pairing Session Communication:

**Starting a Pairing Session:**

```
"Alright, so let's look at this together. 
Can you walk me through what you've tried so far?"

"Let me share my screen. Or do you want to drive?"

"Let's start by understanding the problem. 
What's the expected behavior vs what's happening?"
```

---

**During Pairing - Good Practices:**

**1. Ask, Don't Tell**

❌ **Directive (can feel condescending):**
```
"No, do it this way."
"You should use [approach]."
"That's wrong."
```

✅ **Collaborative:**
```
"What if we tried [approach]? What do you think?"
"Have you considered [alternative]?"
"I wonder if [approach] might work here?"
```

---

**2. Explain Your Reasoning**

❌ **Just doing it:**
```
[Takes keyboard, types solution]
"There, that's how you do it."
```

✅ **Teaching moment:**
```
"Let me show you one approach. The reason I'm doing it this way is [explanation]. 
Does that make sense?"
```

---

**3. Check Understanding**

```
"Does this make sense so far?"
"Want me to explain that part again?"
"Following along okay?"
"Any questions about this?"
```

---

**4. Encourage Them to Try**

```
"Want to try implementing that?"
"Go ahead and give it a shot. I'll watch."
"Let's see what happens if you try [approach]."
```

---

#### Saying No (When You Can't Help):

**Formula: Acknowledge + Reason + Alternative**

**Example 1: No Time**

```
"[ACKNOWLEDGE] I'd love to help with this. 
[REASON] Unfortunately I'm on a tight deadline right now. 
[ALTERNATIVE] Can we sync tomorrow? Or maybe [Other Person] 
can help - they know this area well too."
```

---

**Example 2: Wrong Person**

```
"[ACKNOWLEDGE] Good question. 
[REASON] This isn't my area of expertise. 
[ALTERNATIVE] [Person] would be the better person to ask - 
they built that system. Want me to intro you?"
```

---

**Example 3: Too Vague**

```
"[ACKNOWLEDGE] I want to help. 
[REASON] Can you give me more details about what specifically 
you need? 
[ALTERNATIVE] If you can describe the problem in more detail, 
I can point you in the right direction."
```

---

### LESSON 17.3: Setting Boundaries (15 хвилин)

#### Why Boundaries Matter:

- You can't help everyone with everything
- Your own work has priorities
- Teaching takes time
- Saying yes to everything = burnout

---

#### How to Set Boundaries Kindly:

**1. Time-Boxing**

```
"I have 15 minutes right now. Let's see what we can figure out 
in that time?"

"I can help for 30 minutes, then I need to get back to my deadline."

"Let's timebox this to an hour. If we don't solve it, 
we can loop in [senior person]."
```

---

**2. Async vs Sync**

```
"I don't have time for a call right now, but if you post the details 
in Slack, I can take a look and respond when I have a break."

"Can you write up what you've tried? I'll review and give feedback async."
```

---

**3. Redirecting**

```
"This is more [Person]'s area than mine. You'll get better help from them."

"Have you checked the documentation? There's a good guide on this. 
[Link]. If that doesn't help, ping me."

"This might be better as a team discussion. Want to bring it up in standup?"
```

---

**4. Later is Fine**

```
"I'm heads-down right now, but I can help after lunch."

"Can this wait until tomorrow? I'll have more time then."

"End of week I'll have bandwidth. Does that work?"
```

### LESSON 18.1: Async vs Sync Communication (20 хвилин)

#### Understanding the Difference:

**Synchronous (Real-time):**
- Meetings, calls, video chats
- Instant back-and-forth
- Requires both parties present
- Good for: complex discussions, brainstorming, urgent issues

**Asynchronous (Delayed):**
- Slack messages, emails, documentation
- Response when convenient
- Can be thoughtful and detailed
- Good for: updates, questions, documentation, non-urgent

---

#### When to Use Each:

**Use SYNC when:**
- Complex problem needs discussion
- Quick back-and-forth would be faster
- Emotional/sensitive topic
- Brainstorming needed
- Urgent/blocking issue

**Use ASYNC when:**
- Simple question
- Update/status report
- Documentation
- Person is in different timezone
- You need thoughtful response

**Example Decision Matrix:**

```
"Need help understanding this complex architecture"
→ SYNC (screen share would be better)

"What's the API endpoint for user data?"
→ ASYNC (simple factual question)

"We need to discuss the project direction"
→ SYNC (complex, needs discussion)

"Here's my progress update"
→ ASYNC (informational, no immediate response needed)
```
